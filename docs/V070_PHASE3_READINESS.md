# Phase 3 Readiness (Regime / Strategy)

## Что Phase 3 получает
- `FeatureService.snapshot(symbol, as_of, {tf: names}, base)` → `FeatureSnapshot` со строгим `get()`.
- 37 реализованных features v1 с метаданными, единицами, версиями и хэшами формул; MTF без look-ahead.
- Статусы вместо фиктивных значений: стратегия обязана обрабатывать не-VALUE явно.
- Кеш/персистентность снапшотов для воспроизводимости бэктеста.

## Что нужно решить в спецификации Phase 3
1. **Поведение стратегии при не-VALUE.** Предлагаемое правило: нет сигнала, если любой обязательный feature ≠ VALUE. Причина (gap/stale/insufficient) записывается в журнал решения. Частичные решения только по явному списку опциональных features.
2. **Частота снапшотов.** Считать на каждом закрытии базового бара (15m) или только по событию. Определяет нагрузку и объём `feature_values` (38 строк × 96 точек в сутки × символы).
3. **Регламент ingestion.** Research не загружает данные. Нужен планировщик, который догружает последний закрытый бар до вычисления снапшота, иначе получится массовый STALE.
4. **Нормализация между символами.** Сейчас features в единицах своего символа (цена, base-объём). Для сравнения символов нужны z-score/перцентили за скользящее окно — это отдельные features v1, а не изменение существующих.

## Вердикт
**READY** для Phase 3 при условии, что пункты 1 и 3 будут зафиксированы в её спецификации.
