# QRE v0.7.0 — Data Quality Policy (Phase 2)

Главный принцип: **ни один feature не рассчитывается молча на недостаточных, разорванных или некорректных данных.** Все правила живут в одном месте — `app/research/quality.py::DataQualityPolicy`. Индикаторы не проверяют gaps сами.

## 1. Point-in-time
Для решения в момент `as_of` существуют только бары с `close_time <= as_of`. Всё остальное отбрасывается до любых вычислений, ещё в `prepare()`:
- `is_closed=False` → исключается и считается (`open_candle_exclusions`), issue `OPEN_CANDLE`;
- бар, закрывающийся после `as_of` (даже если помечен закрытым) → исключается как «ещё не известный» (`future_exclusions`). Это не ошибка, а время.

## 2. Классификация качества (`QualityStatus`)
| Статус | Когда | Последствие для feature |
|---|---|---|
| VALID | ряд пригоден для окна feature | VALUE |
| MISSING_HISTORY | нет ни одного закрытого бара | INSUFFICIENT_HISTORY |
| INSUFFICIENT_HISTORY | непрерывный хвост короче `min_observations`, и дыра не является причиной | INSUFFICIENT_HISTORY |
| GAP | дыра внутри окна feature | DATA_QUALITY_FAILURE |
| DUPLICATE | два бара с одинаковым open time | весь ряд непригоден → DATA_QUALITY_FAILURE |
| INVALID | чужой symbol/timeframe в ряду, или результат NaN/±inf | DATA_QUALITY_FAILURE / INVALID |
| STALE | нет бара, который должен был закрыться к `as_of` | DATA_QUALITY_FAILURE |
| OPEN_CANDLE | незакрытый бар присутствовал и был исключён | информационно |

Порядок проверки: unusable (DUPLICATE/INVALID) → MISSING_HISTORY → STALE → непрерывность/длина.

## 3. Gap policy
**Запрещено:** forward-fill, backward-fill, интерполяция, копирование предыдущего close, синтетические свечи. Проверяется тестами `NoSilentFillTests`: после `prepare()` в ряду ровно те метки времени и значения, что пришли.

**Правило:** feature считается только на **последнем непрерывном участке** ряда и требует в нём `min_observations` баров. Это и есть решение проблемы Phase 1 «698 из 700»: старая дыра не блокирует индикатор навсегда, а свежая дыра блокирует ровно до тех пор, пока окно из неё не «выедет».

### Gap severity — относительно окна feature
| Severity | Определение | Пример (одна дыра 49 баров назад) |
|---|---|---|
| NO_GAP | в загруженной истории дыр нет | — |
| MINOR_GAP | дыры есть, но все старше окна feature → на значение не влияют | `sma_20` = VALUE |
| MAJOR_GAP | дыра внутри окна → feature недоступен, пока не накопится `min_observations` баров после дыры | `sma_50`, `ema_200` = DATA_QUALITY_FAILURE |
| UNUSABLE | ряд целиком непригоден (DUPLICATE/INVALID/STALE) | все features |

**Методологическое обоснование (почему нет произвольных порогов вида «≤ 2 пропуска»).** Один и тот же пропуск влияет на разные features по-разному именно через размер их окна зависимости, и это окно уже определено формулой:
- оконные статистики (SMA, rolling std, rolling high/low, суммы объёма) зависят ровно от N баров — дыра вне N не влияет, дыра внутри N меняет выборку;
- доходности через дыру становятся многобарными и неправильно масштабированными (`ret_cc` на первом баре после дыры = DATA_QUALITY_FAILURE);
- рекурсивные фильтры (EMA, Wilder ATR) имеют окно = seed + warmup, где вклад данных старше окна ≤ e⁻⁶. Поэтому дыра старше окна влияет на значение меньше чем на 0.25 % веса, а внутри окна — нет.

Итог: порог для каждого feature — это его `min_observations`, выведенный из формулы, а не подобранное число.

**Допуск дыр (`max_gap_bars > 0`) запрещён в v1** (и в `FeatureSpec`, и в `DataQualityPolicy`). `Window` не содержит маркеров дыр, поэтому формула увидела бы бары по обе стороны дыры как соседние: «однобаровая» доходность охватила бы несколько часов. Это и есть молчаливая склейка ряда. Допуск можно вводить только вместе с `Window`, несущим маркеры дыр, и формулами, которые их учитывают (например, стандартное отклонение, исключающее доходности через дыру).

## 4. Stale
Если бар, который должен был закрыться к `as_of` (`floor(as_of) − tf`), отсутствует, ряд — STALE. Использовать более старый бар как «текущий» нельзя: это была бы подмена времени. `FeatureService` загружает на один бар больше требования, чтобы отсутствие последнего бара проявилось как STALE, а не как «достаточная» история.

## 5. Результаты features (`FeatureStatus`)
`VALUE` · `NOT_AVAILABLE` (не реализован или математически не определён, например нулевой базовый объём) · `INSUFFICIENT_HISTORY` · `DATA_QUALITY_FAILURE` · `INVALID` (NaN/±inf/арифметическая ошибка).
Доменная модель `Feature` не позволяет создать статус ≠ VALUE со значением, VALUE без значения или VALUE с NaN. SQLite дублирует это CHECK-ограничением.

## 6. Метрики
`python test.py` показывает блок **Data Quality Metrics** на детерминированном наборе с дырой и незакрытой свечой: valid/missing/gaps/invalid/open-candle exclusions, число insufficient-history событий и сбоев расчёта, а для каждого feature — coverage вместе с разбивкой исключений. Сумма «coverage + исключения» обязана давать 100 %, иначе категория FAIL.
